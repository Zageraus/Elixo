1. Problem statement

Domain: healthcare (clinic management).

Small clinics and independent doctors keep appointments, prescriptions, lab reports and payments in separate notebooks, spreadsheets and chat apps. This causes double bookings, lost reports, prescriptions that can be altered without trace, no control over who can see a patient's records, and no reliable view of revenue or doctor workload.

ELIXOR stores all of this in one relational PostgreSQL database designed to third normal form. The database itself enforces integrity with keys, constraints, triggers and a stored procedure; access is secured with login, roles and row-level rules; analytics come from SQL views; and every multi-step change runs in a transaction. A modern web application (Next.js + Express.js + Prisma ORM) lets three kinds of users work with the data:

RoleCan do
Patientregister/login, keep a health profile (allergies, blood group), find doctors by specialization, book and pay for visits, view prescriptions and reports, upload reports for an AI summary, verify records were not tampered with
Doctorsee their queue with patient allergies, accept/decline/complete visits, issue multi-medicine prescriptions
Adminsee platform-wide analytics, search/filter/page through users, deactivate or delete accounts

3.6 Normalization

Every table has a single-column surrogate primary key, so there are no partial dependencies (2NF). Two violations of the higher forms were found and removed by migration 012:

BeforeViolationAfter
prescriptions.medications: a JSON array of medicinesRepeating group → not 1NFNew table prescription_items, one row per medicine (screenshot below)
payments.patient_id, doctor_idpayment → appointment → patient: transitive → not 3NFColumns dropped; reached through the appointment (screenshot below)

Functional dependencies after the change: in every table the only determinants are candidate keys (id, plus email, wallet_address, license_number, provider_ref, appointment_id in payments, and (prescription_id, line_no)), so all tables are in BCNF. prescriptions keeps patient_id/doctor_id because appointment_id is optional and therefore does not determine them; trigger trg_check_prescription_appointment keeps them consistent when it is set.

Five views: v_patient_dashboard and v_doctor_dashboard (joins behind the appointment lists), v_report_with_analysis (latest AI summary and anchor per report with LATERAL joins), v_admin_analytics (platform aggregates) and v_doctor_weekly_load (GROUP BY doctor and week).

4.6 Transactions

Every change that touches more than one row runs in a single transaction through prisma.$transaction. The helper withAuditUser() opens the transaction and sets app.current_user_id so the audit trigger records who acted.

Delete doctorINSERT notifications · DELETE users (cascades)

4.7 Stored procedure

sp_create_prescription(p_doctor_id, p_patient_id, p_appointment_id, p_notes, p_items jsonb, INOUT p_prescription_id) validates the input (at least one medicine, an active patient), inserts the prescription and one prescription_items row per medicine, and returns the new id. The API calls it from POST /api/prescriptions.

4.9 Indexes

Indexes cover every foreign key, every filter and sort column used by the API (status, dates, role) and the admin search (pg_trgm GIN on name and email), plus a partial index on unused sign-in nonces and an IVFFlat vector index (indexes screenshot in §3.5).

4.10 ORM integration (Prisma)

All table reads and writes go through Prisma models (backend/prisma/schema.prisma, one model per table, relations named after the ER relationships). Raw SQL is used only where the brief allows it: reading views, calling the stored procedure and the row lock, all through Prisma's parameterised $queryRaw. supabase-js is kept only for file storage and the Supabase Auth password check, which are not table queries.

8. Database backup and recovery

Backups use PostgreSQL's native tools. scripts/db-backup.sh runs pg_dump (custom format, compressed, public schema: tables, data, constraints, indexes, views, functions, the procedure, triggers and RLS policies). scripts/db-restore.sh runs pg_restore --clean --if-exists --single-transaction, so a failed restore leaves the target unchanged. Both read DATABASE_URL from backend/.env and fall back to the postgres:17-alpine Docker image if the tools are not installed. Backups are git-ignored because they contain real data.

bash scripts/db-backup.sh                       # -> backups/elixor_<timestamp>.dump
pg_restore --list backups/elixor_<timestamp>.dump  # inspect the contents
RESTORE_URL=<scratch database> bash scripts/db-restore.sh backups/elixor_<timestamp>.dump

12. Project execution walkthrough

One complete flow through the system, showing the input, the processing and the output at each step.

Step 1 — Patient finds a doctor and requests a visit

Input: specialization filter, doctor, date/time, reason. Processing: POST /api/appointments → JWT and role check → Zod validation (future date) → transaction → INSERT appointment → trigger notifies the doctor and writes the audit log. Output: the request appears with status "requested".

Step 2 — Doctor sees the request and the patient's allergies

Input: doctor opens the dashboard. Processing: GET /api/appointments reads v_doctor_dashboard filtered to the doctor, joins payments and allergies. Output: the queue with Accept/Decline buttons and allergy warnings.

Step 3 — Doctor writes a prescription

Input: patient, medicines, notes. Processing: POST /api/prescriptions → transaction → CALL sp_create_prescription → triggers (consistency check, audit, notification) → commit → SHA-256 fingerprint anchored on the blockchain. Output: the prescription is listed for doctor and patient.

Step 4 — Patient sees the prescription and pays

Input: patient chooses a payment method. Processing: POST /api/payments → transaction with SELECT … FOR UPDATE → status and duplicate checks → INSERT payment (amount taken from the doctor's fee on the server). Output: receipt; the appointment shows "Paid".

Step 5 — Patient uploads a report

Input: title, category, file, optional text. Processing: file stored in a private bucket, SHA-256 hash saved with the report, text summarised by the local AI model, hash anchored on-chain. Output: the report card with its AI summary and a "View PDF" link.

Step 6 — Admin monitors the platform

Input: admin opens the dashboard. Processing: GET /api/admin/analytics reads v_admin_analytics; GET /api/admin/doctor-load reads v_doctor_weekly_load. Output: live figures, the weekly load chart and user management.
